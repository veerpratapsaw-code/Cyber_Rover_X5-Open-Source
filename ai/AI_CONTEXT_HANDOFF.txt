B. Radio Latency Realities:
   • Reyax RYLR998 LoRa (915 MHz): Real-world latency is 140ms to 260ms per packet (3-5 Hz).
     At 11 km/h, driving on LoRa causes 1.5 meters of blind travel per command.

   • NRF24L01+PA+LNA (2.4 GHz): Real-world latency is 6ms to 15ms at 50-100 Hz.
     Mandatory for zero-lag high-speed driving.
   • Dual-Radio Hybrid Architecture: Both radios run together on the STM32. NRF24 drives;
     if NRF24 drops for >300ms, the rover automatically clamps speed to <= 1.8 km/h and
     falls back to LoRa through concrete walls.

C. Video & LiDAR Realities:
   • 5.8 GHz Analog Video: Even at 2.5W (HGLRC Zeus), 5.8 GHz dies after 2-3 concrete walls
     (35-50m indoors). A 2.5W VTX without airflow reaches 95°C in 60s and will thermal-throttle

   • 2D LiDAR (YDLIDAR X2) over Radio: Downsampling 3,000 pts/s into 36 sectors (1 reading

   • 2 FPS Video: 160x120 or 320x240 compressed JPEG is ~1.5–3.0 KB. Streams over Sub-GHz GFSK

 12. Switch Architecture & Electrical Standards:

     - SPDT 3-Position sequential switch (Pin 1 to Pin 2 / Pin 1 to Pin 3 / Both Open) uses exactly 2 GPIO pins (Pin 1 to GND, Pins 2 & 3 to STM32 pins).
     - Momentary push button uses 1 GPIO pin (Pin 1 to GND, Pin 2 to STM32 pin).
     - BOOT0/BOOT1 Architecture Documented: BOOT0=0 runs Flash (0x08000000); BOOT0=1, BOOT1=0 enters ST factory ROM bootloader (0x1FFFF000) on USART1 for USB-TTL. Arduino and ESP do not need manual jumpers due to onboard USB chips with DTR/RTS auto-reset circuits.

Step 2.24: Receiver NRF24 SPI Silicon Unresponsiveness & Phantom Link Resolution: [DIAGNOSED & FIRMWARE PATCHED v1.6]
  - Problem & Forensic Log Analysis:
    * The receiver Serial Monitor printed:
      `>>> [HARDWARE NOTICE] NRF24 silicon unresponsive. Auto-recovering... <<<`
      followed immediately by:
      `>>> RF LINK CONNECTED! RECEIVING LIVE DATA FROM REMOTE! <<<`
      `[FRM #2139062079 | 6 Hz] LX:0 LY:0 | RX:0 RY:0 || POTS: [L:0 C:0 R:0] || SW: [TL:0 TR:0 PL:3 PR:15 CKL:31 CKR:63] || MOTOR: [THR:-150 ARM:0]`
      followed 500ms later by Failsafe disconnect.
    * Root Cause Discovery:
      1. Receiver NRF24 Silicon Is Completely Unresponsive on SPI1 (`radio.isChipConnected() == false`).
      2. The message "RF LINK CONNECTED" was a FALSE POSITIVE:
         - When SPI MISO is floating or pulled down, reading register FIFO_STATUS returns 0x00.
         - Since `(0x00 & RX_EMPTY)` is 0, RF24 library's `radio.available()` evaluated to TRUE.
         - Reading 24 bytes from the dead SPI bus clocked in walking-bit shift register noise:
           `SW: [TL:0 TR:0 PL:3 PR:15 CKL:31 CKR:63]` (Binary: 0b11, 0b1111, 0b11111, 0b111111).
           `FRM #2139062079` = `0x7F7F7F7F`! Subsequent frames: `0x3F1F0F0F`, `0x0F070300`, `0x0F0F0F03`.
         - All joysticks clocked as 0, which computed throttle `-(1908 - 0) / (1908 - 80) = -1.0` (slamming motors into phantom full reverse -150)!
      3. Flawed Gatekeeper in v1.5:
         - Line 167 only checked `toggle_l <= 1 && toggle_r <= 1`.
         - It omitted checking `push_l`, `push_r`, `stick_clk_l`, `stick_clk_r` and did not reject all-zero analog data.
      4. Hardware Root Causes for Silicon Unresponsiveness:
         - STM32 Hardware SPI1 NSS (PA4) Trap: PA4 is hardware NSS. If PA4 is not explicitly configured as OUTPUT HIGH before `SPI.begin()`, hardware Mode Fault (MODF) clears the `SPE` bit and disables the SPI peripheral.
         - NRF24 Adapter Board 5V vs 3.3V Trap: If using the black 8-pin adapter board with AMS1117-3.3, connecting adapter VCC to Blue Pill 3.3V drops output to ~2.1V (1.2V LDO dropout), shutting down the radio. Must be wired to 5V!
         - Direct 3.3V power without 10uF - 100uF capacitor causes voltage brownout.
         - MISO/MOSI wiring swap on SPI1 (PA6=MISO, PA7=MOSI).
  - Firmware Fixes Applied in `cyberrover_x5_rover_rx.ino` (v1.6):
    1. Pre-SPI NSS Protection:
       `pinMode(PIN_NRF_CSN, OUTPUT); digitalWrite(PIN_NRF_CSN, HIGH); pinMode(PIN_NRF_CE, OUTPUT); digitalWrite(PIN_NRF_CE, LOW); SPI.begin();`
    2. Gated `initReceiverRadio()`: Requires both `radio.begin()` and `radio.isChipConnected()`.
    3. Gated Loop Packet Processing: `while (radio.isChipConnected() && radio.available() && rxLimit-- > 0)`.

Step 4.17: Powertrain Chattering Elimination, Zero-Crawl Ground Lock & 3.3V Logic Level Benchmark: [COMPLETED & DEPLOYED]
  - Problem & Symptoms Reported by Veer:
    1. Violent jerking / chattering when running motors over teleop link, which persisted even when the serial monitor cable was disconnected from the S3.
    2. When pressing 'W', 'S', or 'A' and immediately releasing it, the PC cockpit shows all grounded (CMD_STOP), but the motors continue running in that direction at slow speed without control or obeying deceleration rules.
    3. User hypothesized logic level mismatch between 5V BTS7960 driver and 3.3V STM32/ESP32, requesting a 30+ year embedded engineering diagnosis and permanent fix.
  - Comprehensive Root Cause Analysis:
    1. Root Cause 1 (Runaway Crawl on Key Release):
       * On STM32Duino (ARM Cortex-M3 TIM4), `analogWrite(pin, pwm)` configures PB6/PB7/PB8/PB9 into Timer Alternate Function mode.
       * When speed dropped below `MIN_DRIVE_PWM` (55), the old code called `digitalWrite(pin, LOW)`.
       * On STM32Duino, `digitalWrite` only writes to the GPIO Output Data Register (BSRR/ODR); it does NOT clear the hardware timer compare register (`TIM4->CCRx`) or detach the timer from the pin!
       * The hardware timer continued outputting PWM at the last compare value (~50 PWM). Because `lastWrittenLeftPwm` cached 0, the function never touched the timer again, leaving the motor crawling at slow speed indefinitely!
       * Fix: Restored the proven baseline from `10_full_drivetrain_and_rgb_led_test.ino`: ALWAYS call `analogWrite(pin, 0)` followed by `digitalWrite(pin, LOW)`. In STM32Duino, `analogWrite(pin, 0)` explicitly writes 0 to `TIM4->CCRx`, pulling PWM duty to flat 0.00% (true 0.00V GND).
    2. Root Cause 2 (Violent Chattering / Jerking):
       * High-Speed UART Saturation: The STM32 was transmitting 100-character ASCII debug strings (`[MOTORS] RAMPING...`, `[STM32] RX CMD...`, `$TEL...`) across `Serial1` (PA9/PA10) at 100 Hz.
       * At 115200 baud, 100 bytes take ~8.7ms. The STM32's 64-byte UART TX buffer filled up, causing `Serial1.println()` to BLOCK the CPU.
       * While the CPU blocked, incoming bytes from ESP32-S3 on PA10 experienced UART Overrun (ORE) and dropped, corrupting 5-byte frames.
       * When frames failed checksum for >350ms, the STM32 Dead-Man watchdog tripped, slamming speed to 0. A valid frame then arrived, ramping speed back up.
       * This rapid cycle of POWER ON -> WATCHDOG TRIP -> POWER ON -> WATCHDOG TRIP caused violent physical jerking!
       * Fix: Removed ALL verbose ASCII logging from `Serial1`! PA9/PA10 is strictly reserved for a 10 Hz compact 10-byte status line (`$M,L,R\n`). Human debug logs are sent exclusively to USB `Serial`.
    3. Root Cause 3 (Wi-Fi MAC Contention on ESP32-S3):
       * `esp_now_send()` was being invoked directly inside `onDataRecv()` (the Wi-Fi ISR callback).
       * In ESP-IDF, calling `esp_now_send` from inside the receive callback causes MAC layer queue lock contention and packet dropouts.
       * Fix: Decoupled telemetry replies into `loop()` at a steady 20 Hz (every 50ms) completely outside the ISR context.
    4. Hardware Reality: BTS7960 (IBT-2) 5V vs 3.3V Logic Level Physics:
       * The IBT-2 board has an onboard 74HC244 octal buffer powered by the module's `VCC` pin.
       * When `VCC` is fed 5.0V, $V_{IH,\text{min}} = 0.7 \times 5.0\text{V} = 3.5\text{V}$. The STM32 outputs 3.3V ($3.3\text{V} < 3.5\text{V}$), placing the control signals in the undefined/marginal logic zone. When motors pull high current, ground bounce dips the signal, dropping PWM pulses and causing chattering.
       * When IBT-2 `VCC` is connected to 3.3V, $V_{IH,\text{min}} = 0.7 \times 3.3\text{V} = 2.31\text{V}$, providing an enormous 0.99V noise-immune safety margin ($3.3\text{V} - 2.31\text{V} = +0.99\text{V}$). The BTS7960 power IC's native input threshold is only 2.2V, so 3.3V drives it 100% cleanly without requiring level shifter boards!
  - Files Updated & Verified:
    * `firmware/cyberrover_x5_stm32_motor_supervisor/cyberrover_x5_stm32_motor_supervisor.ino`: `analogWrite(0)` ground lock restored, slew rates tuned (`ACCEL_STEP = 8.0f`, `DECEL_STEP = 25.0f`, `MIN_DRIVE_PWM = 45.0f`), `Serial1` quieted, watchdog emergency stop perfected.

Step 4.25: Asynchronous Watchdog Underflow Race Condition Resolution & Permanent Fix: [COMPLETED & VERIFIED]
  - Problem & Phenomenon in Rover S3 Bridge Serial Monitor:
    * In Veer's Serial Monitor, `⚠️ [FAILSAFE ENGAGED] Signal lost for >800ms! Auto-STOP dispatched.` was firing at the exact same millisecond or 1ms after receiving a valid packet:
      `13:07:53.225 -> MODE:ARCADE | RATE:15Hz | SEQ:477 | AXIS:...`

    * Notice that failsafe engaged at :53.226 and cleared at :53.270 (only 44ms later). Packets were arriving continuously at 15–17 Hz (every 58ms).
    * Is it a real control problem or only serial monitor visual glitch?
      ANSWER: It is a REAL PHYSICAL CONTROL PROBLEM. When failsafe trips, `forwardToStm32(CMD_STOP, 0)` is sent to the STM32 Motor Supervisor via UART1 (`0xAA, 'S', 0, csum, 0x55`), cutting motor power and causing violent jerking and stuttering every time a telemetry print occurs.
  - Root Cause Analysis (Asynchronous FreeRTOS Core Concurrency & Unsigned Underflow):
    * At line 338 of `espnow_rx_esp32s3_bridge.ino`: `uint32_t now = millis();` was sampled at the start of `loop()`.
    * At line 468: The 10 Hz USB Serial Telemetry Logger executed ~25 `Serial.print()` calls totaling ~250 characters. At 115200 baud, writing 250 characters takes ~17.3 ms and blocks the CPU once the UART FIFO fills.
    * During this 17.3 ms execution, an incoming ESP-NOW packet arrived from the ESP32-CAM gateway.
    * The FreeRTOS Wi-Fi task executed `onDataRecv()`, setting: `lastPacketTimestamp = millis();` (e.g. T = 1015).
    * `Serial.print()` completed, and `loop()` reached line 548:
      `if (!failsafeTripped && (totalPacketsReceived > 0) && (now - lastPacketTimestamp > FAILSAFE_TIMEOUT_MS))`
    * Because `now` was sampled before the serial print (T = 1000) and `lastPacketTimestamp` was set during the print (T = 1015), `now < lastPacketTimestamp`.
    * In unsigned 32-bit integer arithmetic:
      `now - lastPacketTimestamp = 1000 - 1015 = -15 = 0xFFFFFFF1 = 4,294,967,281`!
    * Because `4,294,967,281 > 800`, the watchdog evaluated to TRUE immediately! It dispatched `CMD_STOP` and printed `[FAILSAFE ENGAGED]`.
    * On the very next iteration of `loop()` (at T = 1016), `if (newCyberPacket)` evaluated to TRUE, printed `>>> [FAILSAFE CLEARED]`, cleared the failsafe flag, and dispatched the active drive command!
  - Permanent Engineering Fix:
    1. Fresh Timestamp Sampling: Replaced stale `now` with `uint32_t watchdog_now = millis();` evaluated immediately at the watchdog assertion block.
    2. Signed Delta Calculation:
       `int32_t elapsed_since_packet = (int32_t)(watchdog_now - lastPacketTimestamp);`
       If multi-core concurrency causes `lastPacketTimestamp` to be a few microseconds ahead of `watchdog_now`, `elapsed_since_packet <= 0`, mathematically preventing underflow.
       If genuine signal loss occurs, `elapsed_since_packet > 800` trips reliably.
       Across the 49.7-day `millis()` rollover boundary, signed subtraction remains mathematically continuous and correct.
    3. Removed Stale Timestamp Overwrite: Removed `lastPacketTimestamp = now;` inside `loop()`, ensuring `lastPacketTimestamp` strictly retains the exact hardware physical reception timestamp recorded by `onDataRecv()`.
